## 一、需求理解与设计目标

### 1.1 业务形态（混合形态）

- **智能客服核心**：多渠道接入（Web/H5/App/微信/企微）、多轮对话、RAG 知识问答、情绪识别、人工接管、工单闭环
- **Agent 编排能力**：运营侧低代码编排 Agent 工作流（工具调用、条件分支、定时触发）

### 1.2 非功能目标

| 指标 | 目标 |
|---|---|
| 规模 | 百万级注册用户，日对话峰值 QPS 5000+ |
| 长连接 | 50 万+ 并发会话（WSS/SSE） |
| 首字延迟 | < 800ms |
| 工具调用超时 | < 5s |
| 可用性 | 99.99%（多云双活容灾 + 私有化交付并存） |
| 数据合规 | PII 脱敏进模型、租户隔离、全链路审计 |

### 1.3 多语言职责边界（核心决策）

| 语言 | 定位 | 核心职责 | 选型理由 |
|---|---|---|---|
| **Java** | 业务中枢 | 用户/租户/权限、会话/工单/知识库 CRUD、报表统计、消息通知 | 生态成熟、事务能力强的业务域建模 |
| **Go** | 接入与长连接 | API 网关/BFF、WSS/SSE 百万级长连接、限流熔断、消息路由 | 高并发协程模型，长连接内存占用极低 |
| **Python** | AI 大脑 | Agent 编排、RAG 管道、LLM 网关、Embedding/Rerank、评测 | AI 生态独占，LangGraph/向量检索库齐全 |
| **Vue3** | 交互层 | 用户端、客服工作台、管理后台、Agent 编排可视化 | 生态成熟、组合式 API 适合复杂交互 |

## 二、总体架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        Vue3 前端层                               │
│  用户端(Web/H5) │ 客服工作台 │ 管理后台 │ Agent编排Studio        │
└──────────────────────────┬──────────────────────────────────────┘
                           │ HTTPS / WSS(SSE)
┌──────────────────────────▼──────────────────────────────────────┐
│                   Go 接入网关层（BFF）                           │
│  • 鉴权/租户路由  • 限流/熔断/灰度  • WSS/SSE 长连接网关(百万级)  │
│  • 消息转发与会话路由                                           │
└───────┬──────────────────────────────┬─────────────────────────┘
        │ RPC(gRPC/HTTP)               │ 事件异步
┌───────▼───────────────┐     ┌────────▼─────────────────────┐
│  Java 业务域 (Spring)  │     │  消息总线 Kafka 集群          │
│ • 用户/租户/权限       │────▶│ • 会话事件  • 消息事件        │
│ • 会话/工单/知识库     │     │ • 工单事件  • 审计事件        │
│ • 报表/通知/权限       │◀────│                              │
└───────┬───────────────┘     └────────┬─────────────────────┘
        │ RPC                          │ 消费/下发
┌───────▼───────────────┐     ┌────────▼─────────────────────┐
│   Python AI 域        │     │  数据层                       │
│ • LLM 网关(多模型)    │     │ MySQL8(业务) + Redis(会话缓存) │
│ • Agent 编排          │     │ ES8(BM25+向量混合检索/日志)   │
│ • RAG 管道 + Rerank   │     │ ClickHouse(分析) + OSS/MinIO  │
│ • 工具执行/记忆管理   │     │                               │
└───────────────────────┘     └──────────────────────────────┘
```

### 关键设计原则

1. **单向依赖**：Go 网关持有用户连接，Java 域不直接持有连接，Python AI 域通过 Go 网关的「下行推送接口」将流式回复推给客户端，三方职责单向依赖，避免循环调用。
2. **事件化解耦**：业务动作全部事件化经 Kafka 异步流转（会话事件、消息事件、工单事件、审计事件）。
3. **AI 域隔离**：Python AI 域不直接访问业务库，仅通过 RPC/事件与 Java 域交互，保证业务数据安全边界。

## 三、技术选型方案

### 3.1 前端层（Vue3）

**主方案：Vue3 + Vite + TypeScript + Pinia + Naive UI**

Naive UI 的 TS 类型完善度与主题定制能力更适合工作台/编排 Studio 类重交互场景。

**技术要点**：

- 流式渲染：`fetch + ReadableStream` 解析 SSE 增量
- 会话高并发推送：WSS
- 图表：ECharts；前端状态机（可选）：XState

### 3.2 网关层（Go）

**主方案：自研 Go BFF 网关**（Gin + gorilla/websocket 或 gnet）

完全掌控长连接语义与业务路由，百万连接实测内存 < 200MB。

内置能力：令牌桶限流、滑动窗口熔断、JWT/租户鉴权、会话粘性路由（hash 到 Java 域实例）、消息完整性（序号 + 重传）。

### 3.3 业务域（Java）

**主方案：Spring Boot 3.x + Spring Cloud Alibaba（Nacos + Sentinel + Seata）**

国内云原生生态契合混合云交付，Sentinel 兜底限流，Seata 处理工单等分布式事务。

模块按 DDD 拆分：`user`、`session`、`ticket`、`knowledge`、`notify`、`report`，每个模块独立可部署。

### 3.4 AI 域（Python）— Agent 框架

**主方案：LangGraph + 自研会话状态机**

图式工作流可精细控制工具调用、条件分支、人工接管，编排灵活、可观测性强。

- LangGraph 作为 Agent 运行时承载核心对话链路
- 自研会话状态机负责业务侧状态迁移（人工接管、工单触发）
- 统一 LLM 网关隔离模型接入

### 3.5 LLM 接入 — 纯云端 API 多模型网关

统一 `llm-gateway`（Python）屏蔽各家 API 差异，提供：

- **路由策略**：模型分级（便宜模型打底 + 强模型兜底）
- **超时控制**：首字 10s / 总时长 120s
- **重试**：指数退避，最多 3 次
- **降级**：主模型失败自动切换备用模型

**模型路由池**：

| 模型 | 优势场景 | 成本(量级) | 路由角色 |
|---|---|---|---|
| DeepSeek-V3 | 常规问答/工具调用，性价比极高 | ★ | 主模型首选 |
| 通义千问 qwen-max/qwen-plus | 中文理解、函数调用稳定 | ★★ | 主模型备选，阿里云合规 |
| 智谱 GLM-4.x | 推理/Agent 任务 | ★★ | 复杂推理兜底 |
| Kimi | 超长上下文文档 | ★★★ | 文档问答专用 |
| GPT-4o/o 系列 | 复杂推理、多模态 | ★★★★ | 高价值场景备用 |

**路由策略**：

- 常规问答 → DeepSeek-V3 / qwen-plus
- 复杂推理 → qwen-max / GLM
- 文档长上下文 → Kimi
- PII 高风险场景强制走私有化小模型（预留接口）

### 3.6 RAG 管道 — 混合检索 + Rerank（强制）

```
用户Query → Query改写/扩展 ─→ 混合检索 ─→ 精排Rerank ─→ 拼装Context → LLM
                        │BM25(ES) + 向量检索(ES kNN)│
```

**主方案：Elasticsearch 8.x（BM25 + kNN 混合检索）**

一套集群同时承担全文检索与向量检索，避免引入独立向量库组件；经 Rerank 后精度与专用向量库差距 <2%。

Rerank 使用 `bge-reranker`（云端 API 或自部署），Top-K 从 20 精排到 5 再入模型。

### 3.7 数据与中间件

| 组件 | 选型 | 说明 |
|---|---|---|
| 业务库 | MySQL 8.0 + ShardingSphere | 会话/工单按租户+时间分片 |
| 缓存 | Redis Cluster | 缓存、会话状态、限流计数、分布式锁 |
| 消息 | Kafka 3.x 集群 | 事件总线，跨域解耦 |
| 分析 | ClickHouse | 会话漏斗、满意度、Token 消耗审计 |
| 对象存储 | OSS（公有云）/ MinIO（私有化） | 文件、知识库附件 |
| 可观测 | Prometheus + Grafana + Loki + OpenTelemetry | 全链路 Trace 贯穿 Go/Java/Python |
| 编排 | Kubernetes + Helm + ArgoCD（GitOps） | 多云/私有化统一交付 |

## 四、核心模块设计

### 4.1 多轮对话状态机（Java 会话域 + Python Agent 运行时）

```
IDLE → AI_ACTIVE → (需工具) TOOL_RUNNING → AI_ACTIVE
        │              │
        ▼              ▼
   TO_HUMAN(排队)   HUMAN_CHAT ←→ (转回) AI_ACTIVE
        │
        ▼
   CLOSED(工单归档)
```

**设计要点**：

- 状态迁移事件全部发 Kafka，客服工作台实时同步
- 会话上下文窗口管理：近期 N 轮 + 检索到的知识 + 记忆摘要（分层压缩）

### 4.2 Agent 工具调用（Function Calling）

- **参数校验**：JSON Schema 强校验 + 类型/枚举/范围白名单
- **异常兜底**：工具执行失败 → 重试 1 次 → 降级为「无工具回答」，并向用户说明
- **安全**：工具白名单、敏感操作二次确认、调用全量审计
- **典型工具集**：查订单、查物流、退换货申请、库存查询、预约回呼、知识库查询

### 4.3 流式通信（WSS/SSE）

- 增量消息带 `seq` 序号 + `chunk_id`，客户端断连重连后从断点续拉（Go 网关本地缓冲 30s）
- Python 流式输出 → Kafka → Go 网关 → 客户端，端到端首字 < 800ms
- 断连期间会话上下文不丢（Redis 持久化 + Java 域落库）

### 4.4 人工接管与工单闭环

AI 置信度低 / 用户明确要求 / 情绪识别异常 → 触发接管，会话状态切 `TO_HUMAN`，AI 将上下文摘要移交人工；人工会话结束可一键生成工单，工单走 Java 域 Seata 事务流程。

## 五、关键链路时序

### 5.1 一次完整对话

```
用户 ──WSS──▶ Go网关 ──RPC──▶ Java(会话域: 校验/落库/发事件)
                                │ Kafka: session.message
                                ▼
                           Python(Agent编排)
                                │ ① 检索知识(RAG混合+Rerank)
                                │ ② 判断是否需工具 → 执行工具
                                │ ③ LLM网关(超时/重试/降级)
                                │ 流式token
                                ▼ Kafka: ai.answer.chunk
                           Go网关 ──WSS增量──▶ 用户(带seq)
```

### 5.2 人工接管触发

```
AI 低置信度 / 用户要求 / 情绪异常
        │
        ▼
Python 发送接管事件 → Kafka: session.takeover
        │
        ▼
Java 会话域更新状态(TO_HUMAN) → 客服队列 → 客服工作台实时显示
        │
        ▼
人工接管后 → 一键生成工单 → Seata 事务流转
```

## 六、混合云 / 私有化交付架构

| 形态 | 方案 |
|---|---|
| 多云双活（阿里云 + 腾讯云） | 双 K8s 集群、DNS 全局负载均衡、数据库基于云间同步（DTS）做两地三中心、Kafka 跨云 MirrorMaker |
| 私有化交付 | 全套 Helm Charts + 离线镜像仓库 + 一键安装器；LLM 地址可配置为私有化模型网关（vLLM），架构不变 |
| 租户隔离 | 逻辑隔离（默认）+ 大客户独立集群 |

## 七、风险与规避

| 风险 | 规避 |
|---|---|
| 三语言团队协作边界不清 | 以「领域」而非「接口」切分，Kafka 事件 + 契约测试（Pact）保证跨域兼容 |
| LLM 输出幻觉/违规 | 回答兜底策略、敏感词过滤、知识引用标注、上线前评测集（Golden Set）回归 |
| 纯云端 API 数据出域 | PII 脱敏前置（手机/证件/地址正则 + 自定义实体识别）、审计日志、高危场景路由私有模型 |
| 长连接水平扩展 | 连接无状态化，会话状态放 Redis，Go 网关按租户 hash 路由，滚动发布秒级 |
