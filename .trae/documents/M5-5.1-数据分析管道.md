# M5-5.1 数据分析管道 — 实施计划

> 里程碑：M5 平台化 ｜ 任务：5.1 数据分析管道（Java/AI）
> 规划原文：**会话漏斗 / 满意度 / Token 消耗 → ClickHouse → 报表页面**
> 状态：待批准执行

---

## 一、Context（为什么做这一步）

M1–M4 已把「会话闭环 → AI 问答 → Agent 化（工具/记忆/接管/同步通道/编排 Studio/多工作流灰度）」全部交付，但**运营侧完全看不到数据**：没有任何报表页面、没有漏斗、没有满意度、Token 消耗记不到库里。规划里 M5 的第一项就是补齐数据分析管道。

调研发现三项指标的**现有基础差异很大**，这是本任务的主要复杂度来源：

| 指标 | 现状 | 结论 |
| --- | --- | --- |
| 会话漏斗 | 会话域是**内存实现**（重启即丢），且 `SessionEventPublisher` **只有** `publishUserMessage` / `publishTakeover`，**没有 create / 状态迁移 / 关闭事件** | 漏斗缺关键节点 → **必须新增生命周期事件** |
| 满意度 | 全仓 grep `csat/rating/feedback/评价/点赞` **零命中**，用户端无评价入口 | **必须新增采集入口 + 事件 + 落库** |
| Token 消耗 | `openai_compat._log_usage` 仅**非流式**路径记录到**日志**（L122/L283-293）；流式主路径（`stream_chat`/`stream_events`）**无任何 usage 采集**，且请求体未带 `stream_options` | 主路径不可采 → **必须新增流式 usage 采集 + 降级估算** |

预期结果：运营在 `/report` 页面看到「会话漏斗转化率 / Token 消耗趋势 / 满意度 CSAT」，数据由**埋点事件流**驱动、可回放重算，且**不阻塞对话主链路**。

## 二、选型决策（用户已确认，均为推荐项）

1. **分析存储 = 本机 MySQL**（ClickHouse 本机不可用：无镜像 + Docker Hub 历史拉取失败 + native 9000 与 MinIO 9000 冲突）。仓储走**依赖倒置端口**，将来切 ClickHouse 只换 infrastructure 实现。
2. **本期三项全做**：会话漏斗 + 满意度 + Token 消耗（含流式主路径）。
3. **采集路径 = 新增单一分析事件主题** `lingxi.analytics.event`（`type` 区分三类事件，Kafka 主题数 **12 → 13**，实施时校正了立项时的历史 off-by-one 计数），Java 新增 `report` 域消费落库。

本计划自定的其余决策（受既有能力约束，非开放项）：

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 漏斗各阶段判定 | Java 侧**不做「首次」判定**，每条用户消息/AI 回复都发一条 `user_msg`/`ai_replied` 事件；聚合侧用 `LEAST(旧值, 新值)` 归并出**最早时间戳** | 避免在会话域引入「是否首条」的状态判定（会话域是内存实现，判定散落易错）；聚合取 MIN 天然等价于「首次」，且迟到/乱序事件也无害 |
| 幂等 | 明细表 `PRIMARY KEY(event_id)` + `INSERT IGNORE`；**仅当插入成功（影响行数>0）才更新聚合** | Kafka 至少一次语义下同一记录会重投；`event_id` 由生产端生成一次，重投时 PK 冲突即被忽略，聚合不会重复累加 |
| 流式 Token 采集 | 请求体加 `stream_options={"include_usage": True}`；**通过 contextvar 收集**，无需改 `stream/stream_events/stream_tool_answer` 等一串签名；不可得时按 `字符数/4` 估算并标 `estimated=true` | 主路径签名链很长（`session_message → stream_workflow_or_default → 图的 llm 节点 → gateway → provider`），逐层加参数会污染整条链；contextvar 由消费入口设置、provider 内旁路记录、`router` 收尾发布 |
| 满意度归属租户 | 前端**只提交 `session_id + rating + comment`**；由 Java 会话域（内存中持有会话）解析 tenant/user 后发布事件 | 禁止前端传 tenant_id（防越权伪造），与「tenant 由服务端注入」既有原则一致 |
| Token 聚合粒度 | `stat_date(企业所在地时区 Asia/Shanghai) × tenant × provider × model`；`requests` = LLM **调用次数**（含工具多轮，一次调用一条事件） | 多轮工具调用确实是多次计费调用，如实计数比强行合并更可信 |
| 图表方案 | **不新增图表库**：漏斗用 `NProgress` 条形 + 内联 SVG 梯形，趋势用 `NDataTable` + 迷你条形；折线图留待后续引入 ECharts | 本期验收只要「报表页面可看」，避免为此增加依赖与包体 |
| 报表页面路径 | `/report`（与 `/studio` 平级），非 `/admin` | `/admin` 仍是 TODO（属 M5-5.6 运营后台完善）；报表是独立的运营分析页 |
| 报表接口鉴权 | 沿用现状：前端尚无登录态，`tenant_id` 走 query 参数（与既有 `/api/v1/studio/workflows?tenant_id=` 一致） | 与仓库现状一致；越权加固属 M5-5.6/5.7，将在计划中显式登记为遗留项 |

## 四、关键设计细节

### 4.1 幂等链路（防 Kafka 重投导致数值虚高）

```
消费到事件 → INSERT IGNORE 明细表(event_id 主键)
   ├─ 影响行数 = 0（重投/重复）→ 直接 return，不碰聚合   ← 关键
   └─ 影响行数 = 1（新事件）→ 按 type 更新聚合表
```
- 漏斗：`UPDATE ... SET stage_ms = LEAST(COALESCE(stage_ms, ?), ?)`（一会话一行，取最早）
- Token：`INSERT ... ON DUPLICATE KEY UPDATE requests = requests + 1, prompt_tokens = prompt_tokens + ? ...`
- 满意度：`INSERT ... ON DUPLICATE KEY UPDATE`（一会话一条，后评覆盖前评）

### 4.2 指标口径

| 指标 | 口径 |
| --- | --- |
| 漏斗各阶段会话数 | 该阶段有时间戳的会话数（`created_ms` 为分母基数） |
| 相邻转化率 | 阶段 N 会话数 / 阶段 N-1 会话数；另给「相对建会话」累计转化率 |
| 阶段判定 | `created`=建会话；`user_msg`=首条 sender=user 消息；`ai_replied`=首次 AI 回复落库；`handoff`=首次坐席接管成功（含 AI 转人工）；`closed`=会话关闭 |
| Token 消耗 | 按 `stat_date × tenant × provider × model` 汇总 requests/prompt/completion/估算占比/平均首字延迟；**跨租户不合算** |
| 满意度 | 评价数、平均分、**CSAT = rating ≥ 4 的评价数 / 评价总数**、评分分布 1~5 |

### 4.3 流式 Token 采集与三级降级

1. **真实**：请求体带 `stream_options.include_usage=true` → 末帧 `choices:[] + usage:{...}` → `record_usage`。
2. **兼容降级**：若 Provider 因该字段报 400（或响应中始终无 usage 帧）→ 去掉字段重试一次（仅首次，避免每轮都试）。
3. **估算降级**：仍不可得 → `prompt_tokens ≈ len(消息内容)//4`、`completion_tokens ≈ len(已产出文本)//4`，置 `estimated=true`；`first_token_ms` 仍真实采集。

全过程：`record_usage` / `flush_usage` 只在 contextvar 存在时生效；发布走 `asyncio.create_task` 后台任务 + done-callback 记异常（沿用 M4-4.5 的 `_spawn_background` 约定），**绝不 await 阻塞流式输出**；被人工接管中断的轮次按已产出文本估算并照常记录（`status=interrupted`）。

### 4.4 与会话域的关系（重要约束）

会话域是**内存实现**，故分析事件是漏斗的**唯一事实源**：事件体必须自带 `tenant_id`/`channel`/`occurred_at`，**不得回头向会话域查数据**（否则重启后漏斗断基线）。这也意味着：**改造上线前的历史会话不会出现在漏斗里**（新数据从改造后开始累积），需在文档中写明。
