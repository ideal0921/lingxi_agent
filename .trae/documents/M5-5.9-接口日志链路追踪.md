# M5-5.9 API 接口日志链路追踪 — 实施计划

> 里程碑：M5 平台化 ｜ 任务：5.9（新增需求）

> 状态：待批准执行

## 一、Context（为什么做这一步）

现状盘点：

| 层 | 已有能力 | 缺口 |
| --- | --- | --- |
| gateway-go | `middleware/accesslog.go` 把 method/path/status/耗时/租户打 **stdout**；`cmd/gateway/main.go` 装配中间件；管理接口经 `handler/proxy.go` REST 透传到 Java | 无 traceId、日志不落库、无跨端关联 |
| core-java | `RequestMetaFilter` 采集 IP/UA；租户经 gRPC metadata（`x-tenant-id`/`x-user-id`/`x-role`）贯穿；`log` 域 = **业务操作审计**（module/action/result） | 无「接口级调用日志」，无 trace 贯穿 |
| ai-python | FastAPI + `messaging/kafka.py`（生产者/消费者） | 无 trace 接入、无 DB |
| web-vue3 | `views/logs/Index.vue` 系统日志页（筛选 + 远程分页） | 无「接口链路追踪」页 |

关键结论：现有「系统日志」是**业务操作审计**，与本次「**API 接口日志链路追踪**」不是一回事；后者需新增 traceId 贯穿 + 接口调用明细落库 + 链路查询页。

预期结果：一次用户请求在网关/Java/Python 产生的每一段调用都以**同一 traceId** 落库，管理端可按 traceId 查看**完整链路时间线**（哪一段慢、哪一段失败）。

## 二、已确认决策（用户拍板）

| 决策项 | 结论 |
| --- | --- |
| 追踪范围 | **全链路**：网关 → Java → Python，含 Kafka 异步 hop |
| 采集落库 | **各端直写 MySQL**，实现上采用**进程内异步批量写**（有界队列 + 定时/满批 flush；队列满则丢弃并计数告警；写库失败只告警、绝不阻断主链路） |
| 管理端呈现 | 新增独立「接口链路追踪」页 + 链路详情时间线 |
| 采样/保留 | **全量采集**；暂不做清理（永久保留）→ 见 §10 风险 |

## 三、链路契约（跨语言统一）

- **traceId 载体**：HTTP header 与 gRPC metadata 统一用 **`x-trace-id`**；Kafka 消息体 JSON 增加 **`trace_id`** 字段。
  - 为什么 Kafka 用**消息体字段而非 header**：本项目三端 Kafka 消息统一是 JSON 体（Go/Python/Java 消费侧都走 JSON 解析），既有 `request_id`（M4-4.6 建议通道）已是同一范式；改 header 需三端同时改 producer/consumer 配置且跨语言易错，收益为零。
- **链路起点 = 网关**：入站已带 `x-trace-id` 则复用（便于跨端联调/外部系统传入），否则生成 UUID；**回写响应头 `X-Trace-Id`**（便于前端与排障时直接取用）。
- **span 字段**：`span_id`、`parent_span_id`、`trace_id`、`service`(gateway-go/core-java/ai-python)、`component`(HTTP/GRPC/KAFKA/WSS)、`entry`(HTTP 路径 / gRPC 全限定方法 / Kafka topic)、`http_method`、`status`(OK/ERROR)、`status_code`、`tenant_id`、`user_id`、`role`、`client_ip`、`elapsed_ms`、`error_msg`、`started_at`(epoch ms)。
- **采样**：本期全量（预留 `sample-rate` 配置项，默认 1.0），后续可调。
- **不落任何请求体/响应体**（PII 合规红线）。

## 四、表结构

在 `core-java/start/src/main/resources/schema.sql` 追加（`spring.sql.init.schema-locations` 启动时幂等执行，风格对齐既有表：注释齐全、epoch ms、utf8mb4）：

```sql
CREATE TABLE IF NOT EXISTS lingxi_api_trace (
    span_id        VARCHAR(64)  NOT NULL COMMENT 'Span ID（UUID）',
    trace_id       VARCHAR(64)  NOT NULL COMMENT '链路 ID（网关生成，三端贯穿）',
    parent_span_id VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '上游 Span（用于还原调用关系）',
    service        VARCHAR(32)  NOT NULL COMMENT '来源服务：gateway-go/core-java/ai-python',
    component      VARCHAR(16)  NOT NULL COMMENT '类型：HTTP/GRPC/KAFKA/WSS',
    entry          VARCHAR(255) NOT NULL COMMENT '入口标识：HTTP 路径 / gRPC 方法 / Kafka topic',
    http_method    VARCHAR(16)  NOT NULL DEFAULT '' COMMENT 'HTTP 方法（非 HTTP 为空）',
    status         VARCHAR(16)  NOT NULL COMMENT '结果：OK/ERROR',
    status_code    INT          NOT NULL DEFAULT 0 COMMENT '状态码（HTTP 状态码 / gRPC 状态码，无则 0）',
    tenant_id      VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '租户 ID',
    user_id        VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '主体 ID',
    role           VARCHAR(32)  NOT NULL DEFAULT '' COMMENT '角色',
    client_ip      VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '来源 IP',
    elapsed_ms     BIGINT       NOT NULL DEFAULT 0 COMMENT '耗时（ms）',
    error_msg      VARCHAR(512) NOT NULL DEFAULT '' COMMENT '错误摘要（截断，不含请求体）',
    started_at     BIGINT       NOT NULL COMMENT '开始时间（epoch ms）',
    PRIMARY KEY (span_id),
    KEY idx_trace (trace_id),
    KEY idx_tenant_time (tenant_id, started_at),
    KEY idx_time (started_at),
    KEY idx_entry (entry)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = 'API 接口链路追踪 Span 表';
```

> 说明：本期**不新增 Kafka 主题、不改动任何 `.proto`**（trace 走 metadata 与消息体字段），因此无需 `scripts/gen-proto.sh` 与四端 proto 重新生成。

## 五、各端改造

### 5.1 Java（core-java）

- **新建 `core-java/trace` 模块**（对齐 DDD 四层：`domain` / `application` / `infrastructure` / `api`），与 `log`（业务审计）语义隔离。
  - `domain/ApiTraceSpan.java`、`domain/repo/ApiTraceRepository.java`
  - `application/ApiTraceBatchWriter.java`：**有界 `ArrayBlockingQueue` + 定时/满批 flush 后台线程**，队列满丢弃并计数、写库异常只 WARN
  - `application/ApiTraceService.java`：入口 `record(entry)`（旁路）+ `page(query,page,size)` + `traceDetail(traceId)`，沿用 `log/application/OperationLogService` 的「不阻断主链路 + `PageResult.of` 分页」范式
  - `infrastructure/repo/MySqlApiTraceRepository.java`：`JdbcTemplate.batchUpdate` 批量插入；`@ConditionalOnProperty(name="lingxi.trace.store", havingValue="mysql", matchIfMissing=true)`（对齐 `MySqlSessionRepository` 的仓储切换范式）
  - `api/ApiTraceController.java`：`GET /api/v1/traces`（列表筛选分页：traceId/entry/status/时间区间，**强制租户过滤**、`@RequireRole({admin})`）、`GET /api/v1/traces/{trace_id}`（该 trace 全部 span 按 `started_at` 升序，用于时间线）
- **`common` 层新增**
  - `TraceContext`（ThreadLocal：traceId / 当前 spanId）+ `TraceIds`（生成/规范化）
  - `TraceIdFilter`（HTTP）：最外层（与 `RequestMetaFilter` 同 `HIGHEST_PRECEDENCE`）读 `x-trace-id`、无则生成、绑定上下文、回写响应头、`finally` 清理（**防线程复用串号**）
  - `TraceServerInterceptor`（gRPC）：从 metadata 读 `x-trace-id` 与身份、绑定上下文、记 span
- **接入点**：`start/config/AuthConfig.java`（注册 Filter）、`start/config/WebAuthConfig.java`（注册 HTTP span `HandlerInterceptor`）、`start/grpc/GrpcServerConfig.java`（注册 gRPC 拦截器）
- **Kafka**：生产侧（`KafkaSessionEventPublisher` 等）消息体注入 `trace_id`；消费侧（`AiReplyConsumer` 等）读 `trace_id` 绑定上下文并记 span
- **配置**：`lingxi.trace.enabled`（默认 true）、`lingxi.trace.store`、`lingxi.trace.batch-size`、`lingxi.trace.flush-interval-ms`、`lingxi.trace.queue-size`、`lingxi.trace.sample-rate`

## 六、关键实现修正（独立校验后的结论，务必照做）

1. **gRPC 拦截器顺序：Trace 放最外层（先注册）**，即 Trace → TenantGuard。Trace 内部**直接读 metadata 里的租户身份**（而不是读 `TenantContext` ThreadLocal，因为此时尚未绑定），从而**能覆盖被租户守卫拒绝的调用**，并在 span 上记录该拒绝结果。
2. **Kafka 一律用消息体 `trace_id` 字段**（不用 Kafka header），与既有 `request_id` 范式一致。
3. **v1 必须覆盖的最小 Kafka 主题集**（保证主链路不断链）：`lingxi.session.message`（用户→AI）、`lingxi.ai.reply`（AI→Java）、`lingxi.ai.chunk`（AI→网关→浏览器）、`lingxi.analytics.event`。`kb.doc.*`、`lingxi.ai.handoff`、`lingxi.tool.audit`、`lingxi.ai.suggest.*` 为旁路通道，v1 可不覆盖（计划内标注为二期）。
4. **HTTP span 的记录点**：`TraceIdFilter` 只负责「绑定/回写/清理」；**span 的落库放在注册于 `AuthInterceptor` 之后的 `HandlerInterceptor`**（`afterCompletion` 早于 Auth 的上下文清理 → 能拿到租户，且登录等豁免路径可一并纳入）。
5. **排除清单**：gateway 中间件需跳过 `/api/v1/health`、`/ws` 与静态资源，不为探活与长连接本身记 span（WSS 只按消息记）。
6. **Java 新模块装配**：根 `pom.xml` 加 `<module>trace</module>`；`trace/pom.xml` 需 `spring-boot-starter-jdbc`（+ 复用父 POM 管理的 MySQL 驱动）；`start/pom.xml` 依赖 `lingxi-trace`；仓储实现用 `@ConditionalOnProperty(name="lingxi.trace.store", havingValue="mysql", matchIfMissing=true)`。
7. **WSS 埋点位置**：`internal/ws/client.go` 的消息收发路径（每条消息一个 span），**不是**升级握手处。
8. 落库一律**旁路**：任何写库异常只告警，不得影响请求结果与首字延迟。

## 八、测试用例（含边界）

**Go**
- trace 中间件：入站**带** `x-trace-id`（复用）与**不带**（生成）两种；响应头回写断言
- writer：满批 flush / 定时 flush / **队列满丢弃并计数** / 底层写库报错不 panic
- proxy：`x-trace-id` 成功透传到下游（httptest 断言下游收到的 header）
- tenant：出站 gRPC metadata 含 `x-trace-id`；缺租户时不注入的既有语义不被破坏
- Kafka 消费：消息含/不含 `trace_id` 两种（缺字段不得 panic）

**Java**
- `TraceIdFilter`：生成/复用、响应头回写、**线程复用不串号**（连续两次请求断言隔离）
- gRPC `TraceServerInterceptor`：**租户被拒的调用仍产生 span**（状态 = UNAUTHENTICATED）、正常调用耗时/状态正确
- 批量写入器：满批、定时、队列满丢弃、写库异常不影响调用方；并发投递不丢
- 查询 API：admin 限权（非 admin 403）、**租户强过滤**（跨租户 traceId 查不到）、时间区间、分页上限（>200 收敛）、trace 详情排序正确
- `schema.sql` 幂等（重复启动不报错）

**Python**
- 中间件：读 `x-trace-id` / 缺省生成；span 字段完整
- writer：批量 flush / 失败隔离 / 停机时 flush 不丢
- Kafka：消费提取 trace、生产注入 trace

**前端**
- `vue-tsc --noEmit` + `vite build` 通过
- 手测：筛选/分页/抽屉时间线；非 admin 不可见菜单

**端到端（验收入口）**
- 门户发一轮问答 → 从响应头取 `X-Trace-Id` → 管理端「接口链路追踪」按该 traceId 查到**跨网关/Java/Python 的 span**，父子关系与耗时正确；其中一个 span 状态为 ERROR 时列表能筛出

## 十、风险与未验证事项（如实标注）

1. **表持续增长**：用户选择「全量采集 + 不做清理」，`lingxi_api_trace` 会随流量线性膨胀；本期以 `tenant_id+started_at`、`started_at`、`trace_id` 索引支撑查询，**保留策略列为后续任务**（届时加分区/归档/清理任务）。
2. **网关首次引入 DB 依赖**：网关此前零数据库依赖，新增连接池需配置合理上限，**DB 不可达时必须丢弃 span 而非阻塞请求**；`GATEWAY_MYSQL_DSN` 为空即关闭写入。
3. **性能红线（首字延迟 <800ms）**：所有落库均旁路异步批量，不进入请求路径；**需端到端复测 TTFT 与改造前对比**（改造前基线：单请求首字 630–1060ms）。
4. **异步批量写的取舍**：进程崩溃时**未 flush 的队列内 span 会丢失**（有界队列 + 丢弃即此代价）；为保证不丢可换 Kafka 管道（与本期用户选择不同，列为备选）。
5. **旁路 Kafka 未覆盖**：`kb.doc.*`、`handoff`、`tool.audit`、`suggest` 在 v1 不记 span，故这些链路在管理端**不可见**（二期补齐）。
6. **多实例未验证**：各端 span 无全局有序保证，多实例/多进程下时间线按 `started_at` 排序可能有同毫秒并列；本期为单实例验证。
7. **未验证项**：管理端页面的窄屏表现、`lingxi_api_trace` 在真实高并发下的写入吞吐、Python 侧 `pymysql` 在事件循环中的实际开销，均需实测后如实标注。
