# M4-4.6 同步通道（坐席快捷回复）实施计划

## Context（为什么做、要达成什么）

AI 对话主路径走 Kafka **异步**事件驱动（低耦合、可削峰），但**坐席快捷回复**是坐在工作台前等待结果的交互：异步链路要经历「投递→排队→生成→回传」，延迟不可控且无同步语义。本任务补一条**低延迟同步通道**，并给它加**并发熔断**，避免挤压主链路。

需求（《工程设计与开发规划》5.4 之 4.6）：gRPC 同步 + 独立并发闸门（32）+ 超时 5s + **超载降级异步**；压测验证不泄漏。域 = Java/Python。

现状缺口：
- **ai-python 无 gRPC 服务端**（只有客户端；生成存根里已有 `Servicer` 基类与 `add_*Servicer_to_server`）。
- **Java 无「调 Python」通道**（目前 Java→Python 仅 Kafka）；`GrpcServerConfig` 用 `ServerBuilder.forPort(9090)` 自动注册 `List<BindableService>`，未自定义线程池。
- 仓库内**无任何信号量/限流实现**；`ToolExecutor`（超时→重试→降级）与 `BusinessToolClient`（惰性建连、线程安全复用）是可复用范式。

## 已确认路线（用户已选定，不提供替代）
1. **语义 = 生成回复建议草稿**：AI 依会话上下文生成 1~3 条候选，同步返回工作台；坐席选择/编辑后自行发送，**AI 不直接对客**。
2. **链路 = Go → Java → Python**：Go 工作台调 Java（Java 组装上下文）→ Java 经**新建出站 gRPC 通道**调 Python。
3. **超载/超时 = 回落 Kafka 异步**：同步接口立即返回「已转异步排队」，结果**推给坐席端**（不复用对客的 `ai.chunk`/`ai.reply`）。
4. **限流在 Python 侧 32**；Java 侧仅设出站超时。

## 关键设计决策（边界与风险）

### D1. Python 服务端用 `grpc.aio`（而非同步线程池）
`LLMGateway.generate` 是协程，`grpc.aio` 服务端可在 FastAPI 事件循环内直接 `await`，**天然不阻塞 loop、无每请求线程**；若用同步 `ThreadPoolExecutor(32)` 则必须 `run_coroutine_threadsafe` 桥接回 FastAPI loop，重造阻塞风险且「线程不泄漏」只能靠数 OS 线程。**并发隔离以 `asyncio.Semaphore(32)` 表达，另设 `maximum_concurrent_rpcs` 作硬顶**（超出由 gRPC 直接拒绝，作为第二道保险）。压测断言「并发任务数回落 + `in_flight==0`」。

### D2. 超时预算分层（Java 出站必须短于端到端）
`Go 5s` **>** `Java 出站 4s`（`lingxi.suggest.timeout-ms:4000`）**>** `Python 单次生成 3.5s`（`suggest_timeout_seconds`）。Java 先到期即自行降级，端到端永不吃满 5s。

### D3. 降级判定落在 Java；`request_id` 贯穿三端
Python 过载以 **gRPC OK + `degraded=true, reason=BUSY`** 返回（非错误态，便于 Java 区分「过载」与「故障」）；Java 收到 BUSY 或 `DEADLINE_EXCEEDED/UNAVAILABLE/RESOURCE_EXHAUSTED` → 调 `SuggestRequestPublisher.enqueue()` 投 Kafka。**Python 侧降级不自投**（唯一入队点，避免重复）。
同步返回「已转异步」与随后异步推送可能同时到达 → 前端按 **`request_id`** 匹配并把「同步已返回的 id」记入 `seenRequestIds`，忽略其异步副本。

### D4. 闸门满 → **立即降级不排队**
`queue_wait_seconds=0`：等待只会把坐席的等待二次放大。请求到达时若 32 路已满，直接转异步。

### D5. 降级不可用时不谎报
Kafka 未启用或投递失败 → `queued=false, degrade_reason="unavailable"`，前端提示「生成失败，请重试」，**不得**谎报「已转异步」。

### D6. 异步结果只推坐席端（防泄漏给用户）
`hub.Broadcast` 无角色概念，若直接广播会把内部建议草稿推给**用户端**。故 `Client` 增 `role`，新增 `Hub.BroadcastToRole(sessionID, "agent", env)`；`ServeWS` 读 `?role=agent`；`NewClient` 保留（默认 `role="user"`），不破坏既有测试。新增信封类型 `suggest`。

### D7. PII 与「不走检索」
建议生成只需「摘要 + 近 N 轮 + 坐席意图」，**不走知识检索**（避免同步路径引入 Milvus/embedding 延迟）。进入模型前用 `PiiMasker` 脱敏、返回前 `restore`（工程强制约束）。

### D8. Java gRPC 服务端线程观测（已知风险，不阻塞交付）
`suggestReplies` 会占用 Java gRPC 服务端默认执行器的线程最长 4s（默认池为无界缓存池：不泄漏但会增长）。本任务限流在 Python 侧（≤32 并发），Go 侧亦有限流，故增长有界；在文档中登记该风险与后续可选改进（为 gRPC server 设定有界 executor）。

## 分步实施（按依赖顺序）

### S1 契约
- `contracts/proto/session.proto`（Go→Java）：`service SessionService` 追加
  `rpc SuggestReplies(SuggestRepliesRequest) returns (SuggestRepliesResponse);`
  `message SuggestRepliesRequest{ string request_id=1; string session_id=2; string agent_id=3; string intent=4; int32 max_suggestions=5; }`
  `message SuggestRepliesResponse{ bool ok=1; bool degraded=2; string degrade_reason=3; bool queued=4; string request_id=5; repeated string suggestions=6; int64 elapsed_ms=7; int32 history_count=8; }`
- 新建 `contracts/proto/agent_sync.proto`（Java→Python，`package lingxi.agentsync.v1`）：
  `service AgentSyncService{ rpc SuggestReplies(GenerateSuggestRequest) returns (GenerateSuggestResponse); }`
  请求 `{request_id, tenant_id, session_id, agent_id, intent, summary, repeated ChatTurn{role,content} history, max_suggestions}`；响应 `{ok, suggestions, degraded, degrade_reason, elapsed_ms}`。
- 重新生成：`bash scripts/gen-proto.sh`（Go/Python）+ `cd core-java && mvn -q -B -pl gateway-api generate-sources`（Java 同时得到 session 服务端/客户端与 agent_sync **客户端** stub）。
**验收**：`go build ./...`、Java 编译通过。

## 端到端验证（真实链路）
前置：重建 Java jar 与重启三端；`scripts/kafka-local.sh init-topics` 建两新主题。
1. **正常路径**：工作台（或 curl）`POST /api/v1/agent/suggest` → `time_total < 5s`、`suggestions` 1~3 条、`degraded=false`、集中日志显示 Java 出站耗时与 Python 生成耗时。
2. **压满 32**：并发 40 个请求（`seq 1 40 | xargs -P 40 …`）→ 断言出现 `degraded=true, queued=true`；`kafka-console-consumer --topic lingxi.ai.suggest.result` 收到同批 `request_id`；工作台收到 `suggest` 信封并渲染候选（**用户端连接不得收到**，验证 D6）。
3. **不泄漏**：5 轮 × 50 请求后静置 10s → Python 进程线程数回到基线、统计端点 `in_flight==0`；再验证第 33 路并发在 5s 内返回「已转异步」。
4. **降级不可用**：`LINGXI_KAFKA_ENABLED=false` 启动 → 过载时返回 `queued=false` 且提示重试（不谎报）。
